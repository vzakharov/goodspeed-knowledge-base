## Child 1 — the document

`docs/design-notes.md`, titled **"Design notes: how the knowledge base works, and why"**. It holds decisions _and_ explanations of how things work, and "decisions" names only the first. ### What it does not repeat

The brief requires the README to carry the architecture decisions and the "more time" list, and it does: `README.md` § "Architecture decisions" already covers the contract package, RLS, the schema, chunking, in-request ingestion, retrieval, streaming, the AI layer, the static export, the API's modules and root-level lint. It does not restate the README's paragraph. The README gains one line pointing at the document, under § "Architecture decisions". ### How it is written

- **/plainly, for a bystander.** Load `.claude/skills/plainly/SKILL.md` before drafting, and run its pass over each section before committing it: cause first, the reader's nouns, a chain rather than a list. Each entry opens with its answer.
- **Standalone.** The document reads as if no review had happened: it never mentions #1, #2, a review, a thread or a T-number, and a reader who has seen none of them loses nothing. The T-numbers in this plan are for the writing session only.
- **Neutral about who knew what.** Each entry is a topic heading and its explanation. Nothing says "the reviewer asked" or "for the record", and no entry is written as a correction. An entry the author understood and one they asked about to learn read the same.
- **Questions the review asked and answered itself get entries too** (T43): the SWC files and the tests' two homes. They are where a reader stops.
- **The thread replies are a start, not the text.** The eleven questions answered in their threads get an entry built from the code, with the reply as a starting point.
- **Reordering is welcome, in every section alike.** #2's order is the order the review met things in, not a reader's: Turborepo at the end of §3 is the plain case. The writing session is free to move entries wherever they read better, in §3 and in the others the same way.
- **Code is cited as `path:line` links**, relative to the repo, so the document can be read with the code beside it.
- **Where the history is the answer, it says so plainly.** The static export came in with the frontend foundation the spin-off carried over (`31586b1`). The entry says so, then asks whether it holds up for this app on its own merits.

**S11's "what a real app does"**, researched in `playgramai/playgramapp` (private, so the entry describes the pattern and cites none of its paths, channel ids, secret names or hosts):

- **One wrapper at every server entry point.** Every server action goes through `safeAction(name, gate, …)`. The gate checks access and contributes who is calling (member, workspace, or IP and user agent when unauthenticated). The wrapper never throws: it returns data or a sorted error, showing the message of a user-facing or validation error and a generic one otherwise.
- **One structured line per stage.** `started`, `succeeded`, `redirected`, `40x`, `failed`, each carrying the action, its nested path through other actions, the caller, shaped inputs and output, the duration, and a correlation id that nested actions inherit and the user's error toast shows as a reference. The logger (pino, JSON to stdout) truncates long payloads centrally, writes a `started` line only for a call still running after a second, and routes stray `console.*` output into single rows.
- **No vendor.** The hosting platform's log store holds the lines. A monitor writes alarm lines when failure ratios cross a threshold, and a scheduled workflow files an issue on them.
- **`/log-review`, an agent over that stream.** Daily, it fetches every line since its last run, probes them, and writes a usage readout (by action path, rejections, latency) plus one deduplicated issue per error. It works only because every line has the same shape.

The entry contrasts that with this codebase's two `Logger` calls, and names the order a real app would add it in: the wrapper and its line shape first, since the review loop depends on them.

The sweep also weighed and dropped two: the configured model name interpolated into a query filter (it comes from config, not users), and the provider's error text reaching the client (documented as deliberate).
